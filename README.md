# Homelab — Infrastructure as Code
An educational project built while learning toward a Linux sysadmin role, with a longer-term direction toward DevOps. It demonstrates reproducible infrastructure as code (IaC) — brought up from scratch with a single command, with no manual configuration steps. Built as a portfolio piece and a way to practice tools from both areas: Vagrant, networking, Ansible, Docker, monitoring, backups, CI/CD.

This is intentionally **not** a lab meant to run 24/7 — it's a disposable environment: the value is in being able to reproduce the entire stack from code, on demand, rather than in keeping something permanently online.

## Project goal

Simulate a small but complete infrastructure lifecycle for a sample web application — a reverse proxy, two application instances, a database, and a monitoring stack — all defined as code and reproducible in a few minutes via `vagrant up`.

## Network topology

Private network (host-only): `192.168.33.0/28`

| Machine      | IP             | Role                          | RAM     | vCPU |
|--------------|----------------|--------------------------------|---------|------|
| `lb`         | 192.168.33.2   | Reverse proxy / entry point    | 2048 MB | 1    |
| `app1`       | 192.168.33.3   | Application instance #1        | 4096 MB | 2    |
| `app2`       | 192.168.33.4   | Application instance #2        | 4096 MB | 2    |
| `db`         | 192.168.33.5   | Database                       | 4096 MB | 2    |
| `monitoring` | 192.168.33.6   | Prometheus + Grafana            | 2048 MB | 1    |
| `registry`   | 192.168.33.7   | Local Docker registry          | 2048 MB | 1    |

Each machine also has a default NAT adapter (internet access, e.g. for `apt`), not directly reachable from the host.

Access from the host:
- SSH to any machine directly via its private network address, using the administrator's key (see below)
- HTTPS to `lb`: `https://127.0.0.1:8443` → forwarded to port 443 on `lb`, terminated with a self-signed cert generated by Ansible
- HTTP to `lb`: `http://127.0.0.1:8080` → forwarded to port 80 on `lb`, which redirects to the HTTPS port above
- Grafana dashboard: `http://192.168.33.6:3000`, reached directly over the private network (no forwarded port — `monitoring` isn't exposed via NAT the way `lb` is)
- `app1`/`app2`/`db`/`registry` are not directly exposed to the host outside the private network — application traffic is intended to reach them only through `lb`

All machines run the same base box (`ubuntu/jammy64`) — a machine's role comes entirely from what gets installed/configured on it via Ansible, not from a different base image ("golden image" approach).

## Prerequisites

- [Vagrant](https://developer.hashicorp.com/vagrant)
- [VirtualBox](https://www.virtualbox.org/)
- Your own SSH key pair (not included in this repo) — generate one locally, e.g.:
  ```bash
  ssh-keygen -t ed25519 -f ./homelab_key -C "homelab"
  ```
  then place the **public** key (`homelab_key.pub`) at `vagrant/shared/key.pub`, and keep the private key (`homelab_key`) somewhere outside the repo — its path is what `SSH_KEY_PATH` in `.env` needs to point to (see [Running the Ansible controller](#running-the-ansible-controller) below).
- [Docker](https://www.docker.com/) (for the Ansible controller container)

## Secrets (Ansible Vault)

Two real secrets exist in this project — the Postgres password and the Grafana admin password — and both are encrypted with [Ansible Vault](https://docs.ansible.com/ansible/latest/vault_guide/index.html) rather than kept as plaintext, even in a homelab, since the whole point of demonstrating this is to do it properly, not as security theater.

The Vault password itself is **not** committed (same reasoning as the SSH key: it's the key that unlocks the secret, so it can't live next to the thing it protects). Before running any playbook that touches `db`, `apps`, or `monitoring`, generate your own:

```bash
openssl rand -base64 32 > vault/pass.txt
```

Then encrypt your own passwords with it, pasting each output into the corresponding `vault.yml`:

```bash
ansible-vault encrypt_string 'your-db-password-here' --name 'db_password' > inventory/group_vars/db/vault.yml
ansible-vault encrypt_string 'your-grafana-password-here' --name 'grafana_admin_password' > inventory/group_vars/monitoring/vault.yml
```

(the Postgres password is mirrored into `inventory/group_vars/apps/vault.yml` too, since the app containers need the same value to connect).

> **Note:** the encrypted values committed in this repo were encrypted with the author's own Vault password — they're not usable by anyone who clones the repo without generating their own `vault/pass.txt` and re-encrypting their own passwords, exactly as intended.

`vault/pass.txt` is mounted into the Ansible controller container (see `.env`/`docker-compose.yml` below), and `ansible.cfg` points to it automatically — no `--ask-vault-pass`/`--vault-password-file` flag needed on every command.

> **Note on `no_log`:** every task that passes a Vault-encrypted secret into a container's environment (`db_password` for the `db` and `apps` containers, `grafana_admin_password` for the `grafana` container) has `no_log: true` set. Without it, the decrypted value could end up printed in Ansible's own output at higher verbosity (`-v`/`-vvv`) or in an error message — the value is safe at rest in the encrypted `vault.yml`, but `no_log` is what keeps it from leaking in transit through Ansible's own logging.

## Bringing the environment up from scratch

```bash
cd vagrant
vagrant up
```

This provisions all six machines, sets up the private network, and installs the administrator's public key into `authorized_keys` on each of them.

Logging into any machine:
```bash
ssh -i <path_to_your_private_key> vagrant@192.168.33.X
```

Tearing everything down:
```bash
vagrant destroy
```

## Running the Ansible controller

The Ansible controller runs inside a Docker container rather than on the host directly, to keep the environment self-contained and independent of what's installed locally.

Create a `.env` file in `ansible/` (not committed — see `.gitignore`) with the path to your private key and your Vault password file:
```
SSH_KEY_PATH=<path_to_your_private_key>
VAULT_PASSWORD_PATH=<path_to_your_vault_pass_file>
```

Then:
```bash
cd ../ansible
docker compose run --rm ansible
```

(Alternatively, skip the `.env` file and set both as environment variables before running the command — `docker-compose` picks up either.)

This drops you into an interactive shell inside the controller, with the project files mounted at `/ansible` and the private key copied and secured at `~/.ssh/homelab_key` inside the container. On start, the container also populates `~/.ssh/known_hosts` for all six VM addresses via `ssh-keyscan`.

> **Important:** make sure all six VMs are fully booted (`vagrant up` finished, SSH responsive) *before* starting the Ansible controller container. `entrypoint.sh` currently has no retry/wait logic around `ssh-keyscan` — see [Known limitations](#known-limitations--technical-debt) below.

Test connectivity:
```bash
ansible all -m ansible.builtin.ping
```

> **Note:** if the controller container cannot reach the VMs over SSH (`Connection timed out`), check Windows Firewall — see [Troubleshooting notes](#ansible-controller-docker-could-not-reach-the-vms-over-ssh--windows-firewall) below.

Provision the entire stack, in the correct order, with a single command:
```bash
ansible-playbook playbooks/site.yml
```

## Playbooks

### `site.yml`
The single entry point for provisioning the whole stack. Imports every other playbook, in the order their dependencies require: base config and firewall first, then the Docker engine (needed by everything below it), then the registry (needed before anything can pull an image from it), then the database, then the application containers, then the reverse proxy (needs the applications already running, since it proxies to them by IP), and finally monitoring (needs `node_exporter` present on every host it scrapes, and the applications/`lb` already up to have anything meaningful to observe).

### `base_setup.yml`
Baseline configuration applied to all six machines: updates the `apt` cache, installs a small set of common tools (`git`, `curl`, `nano`, `htop`), and sets the system timezone to UTC.

### `firewall_setup.yml`
Configures UFW on every machine, with rules scoped per host group (`apps`, `db`, `monitoring`, `lb`) rather than a single `hosts: all` play with `when` conditions. This keeps each group's rules self-contained and readable, and maps cleanly onto future Ansible roles (each group's play is already structured as a natural candidate for extraction into its own role).

The playbook enforces least-privilege access between machines even though they all sit on the same subnet — e.g. `db:5432` only accepts traffic from the two known application server IPs, not from `lb` or `monitoring`, even though network segmentation alone wouldn't prevent that (segmentation only isolates the private network from the outside; it doesn't restrict traffic *within* it).

SSH access is allowed from two distinct sources, corresponding to the two ways a connection can reach a VM: `10.0.2.2` (the host, when connecting directly via `vagrant ssh`/`vagrant provision` over the NAT adapter) and `192.168.33.1` (the host, when connecting via the Ansible controller container over the private network). These were identified empirically via `auth.log` while debugging SSH connectivity.

`lb`'s ports 80 and 443 are allowed only from `10.0.2.2` — the NAT gateway, i.e. the only source that ever reaches `lb` over HTTP/HTTPS, since that traffic always arrives via `forwarded_port` from the host, never directly over the private network from another VM. `192.168.33.1` was deliberately **not** added here, unlike the SSH rule above: there's no actual use case for reaching `lb` over HTTP/HTTPS from the Ansible controller or another VM, and adding it anyway would just be provisioning "for later" without a real need — see the note on `to_ip` below for why this distinction between the two traffic sources matters for more than just scope.

`monitoring`'s port 3000 (Grafana) is allowed from `192.168.33.1` — the host's own address on the private network, since (unlike `lb`) `monitoring` has no `forwarded_port` in the `Vagrantfile` at all; it's reached directly over the private network, the same way SSH is, not through NAT.

`node_exporter`'s port `9100` is a new, reversed direction compared to every other rule in this file: `monitoring` initiates the connection *to* each of the other five hosts, rather than the other way around. A rule allowing `192.168.33.6` (the `monitoring` host) is added to `app1`/`app2`/`db`/`registry`/`lb`, all with `to_ip` scoped to each host's own `ansible_host`, since this traffic stays entirely within the private network — no NAT/forwarded-port layer involved, unlike SSH or `lb`'s HTTP/HTTPS rules.

Play order is deliberate and important: allow rules (SSH, per-group roles) are applied first, then default deny/allow policy, then `ufw enable` last. Reversing this order risks locking out SSH access mid-run.

### `docker_setup.yml` + `roles/docker`
Installs Docker Engine via the official Docker apt repository (GPG key, repo entry pinned to the detected Ubuntu release, then `docker-ce`/`docker-ce-cli`/`containerd.io`/`docker-compose-plugin`) and adds the `vagrant` user to the `docker` group. Written as a role rather than inline tasks, since the installation logic is entirely generic — it doesn't depend on anything specific to this project and could be reused as-is elsewhere.

A second play in the same file, scoped to `apps` only, templates `/etc/docker/daemon.json` with `insecure-registries` pointing at `192.168.33.7:5000` and restarts Docker via a handler. This isn't part of `roles/docker` itself, since the registry's address is specific to this project, not something a generic "install Docker" role should know about. Without it, Docker refuses to pull from the local registry at all, since it has no TLS certificate.

`lb` is deliberately excluded from this role — it doesn't run anything containerized (see `lb_setup.yml` below for why), and provisioning Docker on it "just in case" would go against the same principle applied everywhere else in this project: install what a decision has actually been made to need, not what might conceivably be useful later. `monitoring` **is** included, since it does run Docker (Prometheus + Grafana) — see `monitoring_setup.yml` below.

### `docker_registry_setup.yml`
Runs the local Docker registry (`registry:2`) on the `registry` host and locks down access to it. Kept as a plain playbook rather than a role, since — unlike `roles/docker` — its content (image name, port, the specific IPs allowed to pull) is entirely specific to this project and this one host, not something reusable elsewhere.

Two things worth calling out about how container access is restricted here, since they weren't obvious going in:

- **UFW does not control traffic reaching a published container port.** Docker manages its own `iptables` rules (in the `DOCKER` chain) to route traffic to a container's published port, and those rules are evaluated *before* UFW's own chain — so a UFW rule scoped to specific source IPs has no effect on who can reach the container, even though `ufw status` shows it as active and correctly configured. This was caught empirically: a request from a host that should have been blocked went through anyway. Access control for published container ports has to happen in the `DOCKER-USER` chain instead — the chain Docker explicitly leaves for user-defined rules, evaluated before its own. The playbook adds `RETURN` rules there for the allowed IPs, followed by a `DROP` for the rest, in that order (rule order matters — `DROP` must land *after* the `RETURN` rules, not before).
- **`iptables` rules don't survive a VM restart on their own.** Unlike UFW (which persists its rules via its own systemd service) or Docker (which persists container state itself), rules inserted directly via `iptables` live only in the kernel's in-memory table and are lost on `vagrant halt`/`vagrant up` — even though the container itself comes back fine via `restart_policy: unless-stopped`. The playbook installs `iptables-persistent` and explicitly runs `netfilter-persistent save` *after* the `DOCKER-USER` rules are added, so they're restored automatically on boot without needing to re-run Ansible after every restart.

The same `DOCKER-USER` + `iptables-persistent` pattern established here is reused, unchanged in approach, by `docker_db_setup.yml` and `app_setup.yml` below. Neither `lb` nor `monitoring` ever needed this pattern — `lb` runs no containers at all, and `monitoring`'s only externally-reachable container port (Grafana's `3000`) is controlled with a plain UFW rule instead, since the same DOCKER-chain-bypass problem applies there too, but at this project's current scale a single published port didn't seem to warrant introducing the `DOCKER-USER` pattern for just one rule — worth revisiting if `monitoring` ever exposes more than one port.

### `docker_db_setup.yml`
Runs Postgres (`postgres:16-alpine`) on the `db` host, with `DOCKER-USER` rules restricting access on `5432` to `app1`/`app2` only. Uses a bind mount (`postgres_data_path` → `/var/lib/postgresql/data`) rather than a named Docker volume, so the data lives at a known, explicit path on the VM's own filesystem — chosen deliberately with the future "Backups and restore testing" milestone in mind, since a plain directory is trivial to point a backup script at, where a named volume would require going through Docker itself to get at the same files. Verified empirically that data survives both `vagrant halt`/`up` and a full container recreate.

The Postgres password is Vault-encrypted (see [Secrets](#secrets-ansible-vault) above) and lives in `inventory/group_vars/db/vault.yml`, alongside the plaintext connection details (`inventory/group_vars/db/vars.yml`). The task that passes it into the container's environment has `no_log: true` set.

### `app_setup.yml`
Runs the `counter-app` container (pulled from the local registry) on both `app1` and `app2`, with `DOCKER-USER` rules restricting access on `3000` to `lb` only — set up ahead of time, even though `lb` wasn't running anything yet at the time this playbook was first written.

Each instance gets `INSTANCE_NAME` set to `{{ inventory_hostname }}`, which resolves to the host's alias (`app1`/`app2`) rather than its IP, since `inventory/hosts.yml` defines hosts by name with the actual address in `ansible_host`. The app returns this value in its response (`served_by`), which is what makes it possible to see, from the outside, which of the two instances handled a given request — the whole point of this app existing. The task that passes the mirrored `db_password` into the container's environment has `no_log: true` set, same as on `db`.

### `lb_setup.yml`
Installs and configures Nginx as the stack's reverse proxy and single point of TLS termination, running on `lb`.

**Nginx here is native (installed via `apt`), not containerized** — the only host in the stack configured this way. Every other containerized service runs in Docker specifically because packaging/versioning matters for reproducibility there (own application code, or third-party service images). `lb` is different: it's the one machine whose entire job is accepting traffic **from outside** the controlled private network (via `forwarded_port`). Reusing the `DOCKER-USER` pattern here would put the project's only actual externally-reachable port behind the most error-prone part of the whole access-control setup. A native Nginx process plus plain UFW rules is a simpler, well-understood mechanism, with no additional Docker/`iptables` interaction layer to get wrong on the one host where getting it wrong matters most.

**TLS certificate generation is fully automated**, via the `community.crypto` collection (`openssl_privatekey` → `openssl_csr` → `x509_certificate`, `provider: selfsigned`), re-run on every provisioning pass — consistent with the project's "everything from code" philosophy, in contrast to the SSH key and Vault password, which are deliberately kept *outside* automation because they're real secrets requiring manual, out-of-band distribution.

- `common_name` is `127.0.0.1` — the address actually used to reach `lb` from Windows in practice, through the forwarded port, rather than `192.168.33.2` (the private-network address, which is more "canonical" but not what the browser/`curl` actually connects to).
- `subject_alt_name` is `IP:127.0.0.1` only. `192.168.33.2` was deliberately left out: no client in this stack ever actually connects to `lb` over HTTPS using its private-network address — Windows always goes through the forwarded port (`127.0.0.1`), and UFW only allows port 443 from `10.0.2.2` in the first place (see the `firewall_setup.yml` section above), so traffic to `192.168.33.2:443` would be dropped before it ever reached Nginx. Adding it to the cert would just be provisioning for a use case that doesn't exist — the same principle applied to the UFW rule scope. If a real need for that access path ever comes up, it's a one-line addition, re-applied automatically on the next `site.yml` run.

> **Note on `community.crypto` module naming:** the `openssl_certificate` module was removed and renamed to `x509_certificate` in `community.crypto` 2.0.0. Since the Ansible controller's `Dockerfile` installs the `ansible` package (not `ansible-core`), the collection's version isn't pinned — a fresh `docker compose build` can pull a newer `community.crypto` than the one this playbook was originally written against, and the old module name will fail with a clear "module has been removed" error rather than silently misbehaving.

**Reverse proxy configuration** (`templates/nginx.conf.j2`) defines:
- an `upstream` block listing `app1`/`app2` by private-network IP and port `3000` (there's no DNS between the VMs, so Nginx has no way to resolve their inventory names — it needs raw IPs), load-balanced round-robin (Nginx's default, which is exactly what's needed to demonstrate traffic being split across both instances via `served_by`);
- a `server` block on `443` doing TLS termination (pointing at the generated cert/key) and proxying to that upstream over plain HTTP — TLS terminates on `lb` only, and the `lb`↔`app1`/`app2` leg is unencrypted, which is fine since it never leaves the isolated private network;
- a second `server` block on `80` that only issues a `301` redirect to HTTPS.

### `monitoring_setup.yml`
Installs `node_exporter` on every host (via `roles/node_exporter`) and runs Prometheus + Grafana on `monitoring`.

**`node_exporter` is a role, not inline tasks in this playbook** — installed identically on all six hosts (including `lb`, which otherwise runs no Docker at all), so the logic is entirely generic and project-independent, the same reasoning already applied to `roles/docker`.

**Installed as a static binary + systemd unit, not a Docker container**, even on the five hosts that already run Docker. Two reasons: `lb` has no Docker at all, and installing the entire Docker engine there just to run one small monitoring process would be a disproportionate amount of complexity and resource overhead for what it buys; and using the same native-process approach everywhere avoids branching the role's logic by host group, keeping it as one simple, uniform path. The role:
- downloads and unpacks the official release tarball (`ansible.builtin.unarchive`, `--strip-components=1` via `extra_opts` so the binary lands directly in the install directory rather than nested inside a versioned subfolder);
- creates a dedicated, unprivileged system user (`system: true`, no shell, no home directory) to run the process — the same reasoning as not running services as `root`/`vagrant` anywhere else in this project;
- templates a systemd unit and starts/enables the service.

`node_exporter`'s `--web.listen-address` is bound to each host's private-network address (`ansible_host:9100`), not `0.0.0.0` — deliberately, to avoid listening on the NAT interface at all, consistent with the project's general approach of exposing services only on the interface traffic is actually expected to arrive on.

**Prometheus and Grafana run in Docker, in a Docker network created specifically for this pair of containers** (`community.docker.docker_network`), so they can reach each other by container name (`http://prometheus:9090`) via Docker's built-in DNS — something only available on user-defined networks, not the default bridge. Because of this, **Prometheus's port `9090` is not published to the host at all**: the only consumer is Grafana, and it's on the same host in the same Docker network, so there's no reason to expose it any wider than that — the same minimal-exposure principle already applied via `DOCKER-USER` elsewhere. Grafana's `3000` is published, since that's the actual point of contact from outside the containers.

Prometheus's scrape config (`templates/prometheus.yml.j2`) is generated from the inventory itself rather than hand-listing hosts: it loops over `groups['all']`, resolving each host's address via `hostvars[host].ansible_host`, and explicitly skips `monitoring` (self-monitoring is a deliberate scope cut for now, not an oversight — see `defaults`/scope discussion below). The template took a few iterations to get right — Jinja2's whitespace-control tags (`{%-`/`-%}`) needed care: trimming *both* sides of every control tag collapsed the whole target list onto one unparseable line, and trimming everything including the leading `- ` produced YAML that parsed but with completely wrong structure (`targets` ended up holding one mangled string instead of a list). The working version trims only the leading whitespace of each control tag (`{%-`) while leaving the trailing side untouched (plain `%}`), so the newline after each tag — the one separating each rendered target line from the next — is preserved. This was verified by actually rendering the template and parsing the result as YAML, rather than judging it by eye from the source.

The config file itself is a bind-mounted single file (`prometheus_config_path`, host-side), not a bind-mounted directory — deliberately, so only the one file Ansible actually manages gets swapped in, rather than overlaying the whole `/etc/prometheus` directory from the image. On config change, the `template` task notifies a handler that reloads Prometheus via `docker kill -s HUP prometheus` rather than restarting the container — Prometheus supports a SIGHUP-triggered config reload out of the box, no extra startup flags needed, so the running container never has to stop.

> **Note on bind-mount ownership:** the `prom/prometheus` image runs as a fixed, unprivileged UID (`65534`) inside the container, not root. The host-side data directory (`prometheus_data_path`) has to be owned by that same UID for the container to be able to write to it — creating the directory with a `root`-owned default (or worse, `mode: '0777'` as a first attempt at a fix) either fails outright or opens the directory to every user on the host, which is a far bigger hole than necessary. The correct fix is `owner: "65534"` on the directory, matching the actual UID the process runs as inside the container — confirmed empirically via `docker exec prometheus id` rather than assumed from general knowledge about "typical" container UIDs, since that number isn't guaranteed to be the same across every image.

The Grafana admin password is Vault-encrypted (see [Secrets](#secrets-ansible-vault) above) and passed in via `GF_SECURITY_ADMIN_PASSWORD`; the task has `no_log: true` set, the same pattern applied to the Postgres and application containers above.

**Both the Prometheus data source and the dashboard itself are provisioned as code**, via files mounted into `/etc/grafana/provisioning` and `/var/lib/grafana/dashboards` respectively (`grafana_provisioning_path`/`grafana_dashboards_path`, host-side). The data source's `uid` is deliberately hardcoded in `datasource.yml` (rather than left to Grafana's default random generation) so that it matches the `uid` every panel in the dashboard JSON references — without this, a freshly provisioned data source would get a new random `uid` on every `vagrant destroy`/`up`, silently breaking every panel's link to it. The dashboard itself (`node_exporter_overview.json`) is a direct export from the Grafana UI, not hand-written, and covers six panels:

- **Memory usage (%)** and **CPU usage (%)** — Gauge panels, one value per host, thresholds at 60/80 and 70/90 respectively.
- **Network receive/transmit (internal)** — Time series panels, filtered to the `enp0s8` interface only (the private-network one; `lo`, `docker0`, and the NAT-facing `enp0s3` are excluded), using `irate()` for responsiveness on a live-refreshing dashboard.
- **Status (up/down)** — a Stat panel on the raw `up` metric, with Grafana value mappings turning `0`/`1` into "DOWN"/"UP" text, and thresholds colored accordingly.
- **Load average (1m, per-core)** — `node_load1` divided by each host's core count (`count by (instance) (node_cpu_seconds_total{mode="idle"})`, joined via `on (instance)` since the two sides don't share the `job` label), so hosts with different `vCPU` counts are directly comparable rather than reading raw, unnormalized load values.

Verified empirically by deleting the dashboard through the UI and re-running `site.yml` — it reappears automatically, unchanged.

## Building and publishing the application image

Building and pushing the `counter-app` image is a deliberately manual step at this stage, not something `site.yml` does — provisioning infrastructure (Ansible's job) and building/publishing a code artifact are different kinds of work, and the latter already has its own dedicated milestone ahead (CI/CD). Automating it now would mean solving that problem twice.

Docker Desktop can't reach the private network directly (same root cause as the Windows Firewall issue below), so the image has to be built from a machine that's actually on `192.168.33.0/28` — `app1` works well since it's already provisioned:

```bash
vagrant ssh app1
git clone <this-repo-url>
cd <repo>/app
docker build -t 192.168.33.7:5000/counter-app:latest .
docker push 192.168.33.7:5000/counter-app:latest
```

> **Note:** the registry has no TLS certificate (see `docker_setup.yml` above) — a real self-signed cert would need distributing and trusting on every client, which isn't worth the overhead here since all traffic stays inside the isolated private network anyway. `insecure-registries` is a deliberate, documented trade-off, not an oversight.

Since the registry's own container has no persistent storage for pushed images, a full `vagrant destroy` that includes `registry` wipes any previously pushed image — `app_setup.yml` will fail to pull until the image is rebuilt and pushed again.

## Testing the reverse proxy

Once `site.yml` has finished, from Windows:


(`-k` is required since the certificate is self-signed and not trusted by the system.) Run it a handful of times in a row — the `served_by` field in the JSON response should alternate between `app1` and `app2`, which is the visible proof that requests are actually being load-balanced across both instances rather than always hitting the same one.

should return `301 Moved Permanently` with a `Location: https://127.0.0.1:8443/` header.

## Known limitations / technical debt

Documented here deliberately, rather than silently fixed or hidden — these are conscious trade-offs or known rough edges at the current stage of the project, not oversights.

- **`entrypoint.sh` has no retry/wait logic.** The `ssh-keyscan` loop runs under `set -e`; if a VM isn't fully booted and responsive on port 22 yet, the scan can fail and kill the container's entrypoint before it reaches the Ansible shell. Currently relies on always starting the controller *after* all VMs are confirmed up. A more robust version would retry with a timeout instead of failing immediately.
- **`Vagrantfile` defines each machine as a separate, hand-written block** rather than looping over a data structure (e.g. an array of host definitions). At 6 machines this is easy to maintain; adding more machines means copying a block rather than adding one entry to a list. Left as-is deliberately at this scale — a reasonable refactor target if the machine count grows.
- **`community.crypto` is not version-pinned**, since the Ansible controller installs `ansible` rather than `ansible-core` (a deliberate trade-off to get `community.general`/`community.docker` "for free" — see `Dockerfile`). This means module names/behavior in that collection can shift between a fresh container build and the one the playbooks were originally written against, as already happened once with `openssl_certificate` → `x509_certificate`.
- **`monitoring` doesn't scrape itself.** `node_exporter` runs on `monitoring` too, but Prometheus's scrape config deliberately excludes it for now — a scope cut for this first pass at the monitoring stack, not an oversight. Adding it back (via `localhost:9100`, since Prometheus and that particular `node_exporter` instance share the same host) is a small, well-understood addition when needed.
- **No trusted, service-specific Prometheus metrics yet** (Postgres, Nginx, per-container stats via cAdvisor) — this first pass only covers host-level metrics via `node_exporter`. Deliberately scoped this way to get a working skeleton (Prometheus + Grafana + one exporter type, across all hosts) understood end-to-end before adding more exporters and more moving parts at once.
- **No alerting yet.** The dashboard is a "someone has to look at it" tool — nothing currently pages/notifies automatically if a host goes down or a threshold is crossed. The `up`-based status panel and the various threshold colors help at a glance, but only if someone actually opens Grafana; that's a deliberate scope cut for this pass, not a gap that was missed.
- **The host-side UID (`65534`) for Prometheus's data directory is hardcoded**, matching the specific UID the `prom/prometheus` image happens to run as. If the image is ever swapped for one that uses a different UID, this would need updating in step — there's no dynamic lookup of the "correct" UID from Ansible's side.
- **`rate()`/`irate()`-based dashboard panels show artifact spikes after the host machine resumes from sleep.** Suspending the physical host also suspends the VMs and the Ansible controller, creating a gap in Prometheus's scraping. Once scraping resumes, `rate()`/`irate()` computed across two samples separated by far more than the normal scrape interval produce artificially high values right at the edge of that gap — a measurement artifact from the gap itself, not real load. Confirmed empirically by comparing the graph against `top` output on the affected host at the same moment. Not something to "fix" so much as to be aware of when reading the graphs after a period of inactivity.
- **Grafana login sessions don't survive a container recreate.** Only `provisioning/` and `dashboards/` are bind-mounted into the Grafana container, not all of `/var/lib/grafana` — so Grafana's internal session database resets with every fresh container, requiring a fresh login after `vagrant destroy`/`up`. A deliberate trade-off: re-logging in is a trivial, one-time cost per environment rebuild, and the admin credentials are already fully reproducible from Vault either way, so persisting session state didn't seem worth the extra state living outside version control.

## Troubleshooting notes

Issues encountered while building this project, kept here for reference — both for future-me and as a demonstration of the debugging process.

### Intermittent VM boot timeouts (`rcu_sched` stalls)

Symptom: `vagrant up`/`vagrant provision` would occasionally time out on a seemingly random machine, even when run sequentially (`--no-parallel`). Console access (VirtualBox GUI) showed the guest kernel logging `rcu_sched detected stalls on CPUs/tasks` after a multi-minute gap in the boot log timestamps — indicating the VM's virtual CPU wasn't being scheduled time by the host, not a guest-side failure.

Ruled out: parallel resource contention (occurred even one VM at a time), `vagrant-vbguest` plugin (not installed), disk type (host disk is SSD).

Mitigations applied: added the VirtualBox VMs folder to Windows Defender exclusions; increased `config.vm.boot_timeout`. The issue is intermittent and not fully resolved — if it recurs, check Windows power plan settings (minimum CPU state) and whether other virtualization backends (e.g. Docker Desktop/WSL2) are running concurrently, since VirtualBox and Hyper-V-based virtualization can contend for the same host resources.

### Ansible controller (Docker) could not reach the VMs over SSH — Windows Firewall

Symptom: `ansible all -m ping` from the Ansible controller container failed with `Connection timed out` on port 22 for every host, even though the containerized Ansible controller could ping the private network's gateway (`192.168.33.1`) and the VMs themselves without issue.

Root cause: the container (running under Docker Desktop/WSL2) and the Vagrant VMs (running under VirtualBox host-only networking) sit on two independent virtual network segments on the same physical host. Traffic between them has to pass through the Windows network stack, where Windows Firewall was blocking inbound TCP traffic on port 22 from the `192.168.33.0/28` range — while still allowing ICMP (ping), which is why the network layer looked healthy but SSH did not connect.

Fix: added an inbound Windows Firewall rule (TCP, port 22, remote scope restricted to `192.168.33.0/28`, action: allow) rather than disabling the firewall. This was diagnosed step by step by isolating each layer of the connection: routing (`ping` to gateway and hosts) → firewall (temporarily disabled to confirm, then replaced with a scoped rule) → SSH host key verification (`Host key verification failed`, resolved via `ssh-keyscan` populating `known_hosts` in the entrypoint script) → key-based authentication (final success).

Takeaway: when debugging SSH connectivity across virtualized network boundaries, distinguish failure modes by error message — `Connection timed out` points to routing/firewall, `Host key verification failed` points to `known_hosts`, `Permission denied (publickey)` points to authentication — and test each layer independently (ping → port reachability → SSH handshake) instead of changing configuration at random.

> **Note:** this is the only piece of the entire infrastructure that is *not* version-controlled — the Windows Firewall rule has to be recreated manually on any new host machine cloning this repo.
